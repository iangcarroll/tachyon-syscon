# SG560D control reconstruction

`src/sg560d.c` reconstructs the control/poll logic from firmware1.0.52. The
exported `sg560d_execute` dispatches by original entry address for differential
testing, takes a4KiB RAM image, and routes external dependencies through
`sg560d_environment`. This native-test API is not the original calling convention
and is not a complete, linkable, or flashable replacement firmware image.

## Implemented scope

- `0x5e30`: stop UART1, clear its128-byte parser buffer, configure the UART pins.
- `0x5f30`: power-source checks and selection, dead-battery workaround, boot timeout.
- `0x614c`: initialize UART1 at115200 and enable its parser.
- `0x61b8..0x6240`: boot-task callbacks and power-key/volume/USB_BOOT actions.
- `0x6248`, `0x6282`: GPIO/expander pin configuration for off/on transitions.
- `0x62ec`, `0x6384`: thermal/exponential retry delay and retry scheduling.
- `0x6428..0x65e4`: normal, EDL, FASTBOOT and FCT boot-task submission.
- `0x65f0`, `0x6650`: timed wake setup/cancel and remaining-seconds reporting.
- `0x6690`, `0x66a0`, `0x66bc`: off detection, mode-name pointers, and mode changes.
- `0x6720`: power-off sequence, including the active-task exclusion.
- `0x6838`, `0x68a4`, `0x68fc`: FASTBOOT/FCT, EDL and normal boot preparation.
- `0x6948`: initial power-state discovery.
- `0x6a28`, `0x6a48`: power-key assertion/release.
- `0x6a68`: full main poll body, including unexpected-power recovery, RGB sampling,
  timed wake, thermal/retry policy, and USB-restore debounce.
- `0x7468..0x74c8`: timed expander pulses and FCT task callbacks.

The variadic UART printf wrapper at `0x5edc` is reconstructed separately in the
formatting/logging module, using explicit ARM argument-list and memory callbacks.
Its 128-byte truncation, NUL-delimited transmission, and trailing CRLF are checked
against the original code; see `analysis/format-test-instruction-coverage.json`.
It is not routed through `sg560d_execute` and is not replaced by host libc printf.

## State and preserved behaviors

Addresses below are offsets from`0x20000000`; the implementation accesses them
through byte copies to avoid alignment or aliasing assumptions on the host.

| Offset | Recovered role |
| --- | --- |
| `0xed` | UART/parser enabled byte |
| `0x244`, `0x247` | UART1 descriptor TX/RX pin identifiers |
| `0x3c4`, `0x3c8` | FASTBOOT/FCT selected mode and mode-name pointer |
| `0x3cc..0x3ce` | Stable modem RGB signal values |
| `0x3cf` | Awaiting reboot confirmation |
| `0x3d0..0x44f` | UART/parser buffer |
| `0x450` | Current boot mode |
| `0x454` | FCT boot timestamp, low32bits only |
| `0x458` | Timed-wake deadline,64bits |
| `0x4e0` | Modem-up timestamp,64bits |
| `0x4e8` | Dead-battery handback deadline,64bits |
| `0x4f0` | Previous USB-present sample |
| `0x4f1`, `0x4f2` | Observed and expected power state |
| `0x4f4` | Retry attempt count |
| `0x4f8` | Dead-battery workaround active |
| `0x4f9..0x4fb` | Eight-bit modem RGB histories |
| `0x500`, `0x508` | Retry deadline and active byte |
| `0x509`, `0x50a` | USB-debounce active and USB-sample initialized |
| `0x510` | Timed-wake deferral log deadline |
| `0x518` | Power-state transition deadline |
| `0x520` | USB debounce start time |
| `0x528` | Retry reason |
| `0x52c`, `0x530` | Green-on/RGB-change timestamp, low32bits only |

Compatibility quirks retained in the C implementation:

- Boot requests return success after task submission fails; the original only
  logs that failure. The task records, order, delays and callback addresses match.
- RGB goes high after three high samples but goes low only after its entire
  eight-bit history is zero. Some timestamps are truncated to32bits even though
  comparisons use64-bit time; wrap behavior is retained.
- Thermal retry backoff starts at a minimum120seconds at50.0C, doubles by attempt,
  and caps at900seconds. Invalid/new retry reasons can leave older retry state
  active; the original state-update ordering is preserved.
- A timed wake can be deferred by thermal/power-event conditions. USB restoration
  is debounced for5000ms, and existing shutdown/retry ownership affects booting.
- Hardware-driver failures in many power-control paths are logged but do not
  abort the original sequence. Tests preserve the resulting dependency calls.
- Driver assertions are explicit dependency calls. The production assertion
  handler is nonreturning. Test adapters record and return from assertions to
  inspect the remaining instruction path; this is a deliberate test substitution,
  not a claim that failed preconditions are recoverable on the device.

## Validation and boundaries

The12 tests in`tests/test_sg560d.py` passed in local emulation. They include1200
seeded poll scenarios,500 power-source scenarios, targeted branch cases, and
multi-step USB-restore/RGB-debounce flows. Each comparison executes the original
Thumb instructions, compares all RAM bytes through offset`0x7ff`, and compares
ordered external dependency calls and structured GPIO/UART/task payloads.

The main poll at`0x6a68` exercised all978 mapped instruction addresses. Its missed
paths after the random pass were deliberately exercised using recovery, brownout,
64-bit elapsed-time and USB ownership/debounce cases. The exact invocation and
address evidence are in`analysis/sg560d-test-instruction-coverage.json`.
Instruction coverage does not establish all combinations of states or physical
hardware behavior. The15 unexecuted instructions in UART stop are the
null-descriptor assertion path: the actual`hal_uart_info(1)` routine always
returns the fixed, nonzero RAM address`0x20000244`. The format wrapper has its own
tests and report in the formatting/logging module.

The environment explicitly substitutes power-manager readings/actions, parser
ingestion, GPIO/UART drivers, LED and power-key updates, time, and task submission.
Higher-level tests also substitute lower SG560D setup routines; those routines
have separate differential tests. The components have not yet been composed into
a complete board emulator or a real asynchronous task/interrupt integration.
Diagnostic logging is excluded from the C output and is hooked in the oracle.
No hardware was accessed or programmed.

Run:

```sh
syscon-re/.venv/bin/python -m pytest -q syscon-re/tests/test_sg560d.py
```
