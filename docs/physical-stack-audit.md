# Physical image stack audit

This is a conservative static diagnostic, not a whole-image stack proof. The frozen input snapshot is `build/physical-stack-audit/`: ELF, 58 compiler `.su` files, build manifest, and `snapshot.json` hashes. `tools/audit_physical_stack.py` writes `analysis/physical-stack-audit.json`. It never accesses hardware or writes a firmware image.

This historical snapshot includes the source scanner EOF callback and FILE `_read` handling, the inlined CONFIG_SET logging helper, and the source-defined NUL data byte at `0x2919`. The final refresh also includes the UART original-frame ABI adapter, logger output-register preservation, and corrected config-slot checksum-byte read order. These were the ELF and `.su` inputs at that checkpoint. The current implementation has removed the compatibility byte and slot-writing assembly adapter; use freshly generated build/stack reports for current frame sizes.

The snapshot ELF SHA-256 is `ae534a6640d592194d4aa86198e8b5d8cefbc94172bb07854c251e99e3a2335a`. The corresponding canonical binary SHA-256 is `8b9a3cf653b32c374b21f3b89ccf0161fc54a30d018710e61eca9bbe989c9461`. Its initial MSP is `0x20001000`; fixed RAM and additional globals end at `0x20000820`. The nominal available stack span is 2,016 bytes. That address subtraction does not prove that all paths fit.

The audit enumerates 454 linked function entry addresses, merging aliases. ELF local-file ownership disambiguates repeated static function names when matching compiler frames. It follows direct instruction branches and calls, detects recursive call-graph components, and leaves mutable indirect calls, computed jumps, missing assembly metadata, dynamic SP adjustments, and uncertain exits unresolved. A separate local SP walk checks fixed PUSH/POP and immediate SP changes against compiler frame metadata. Compiler reports alone are insufficient.

A concrete discrepancy occurs in `syscon_rt_sscanf` at `0x2060`: its `.su` record says 116 bytes, while the actual prologue pushes R1–R3 (12 bytes), pushes LR (4 bytes), and subtracts 112 bytes from SP: **128 bytes before calling the scanner**. The extra saved variadic argument registers must be counted. The audit rejects the compiler-only bound for this function rather than silently using 116. The scanner and config compaction functions also use register-based SP adjustments that this deliberately small analyzer leaves unresolved.

A possible recursive component includes assertion, logger, diagnostic UART, and GPIO paths: assertion calls the logger; logging can write the diagnostic UART and exercise GPIO; invalid state can reach assertion again. This is a static potential cycle, not an observed recursive execution. A finite bound requires an invariant that excludes the cycle or a depth argument. The current analysis establishes neither.

There are 192 closed synchronous direct-call bounds under the report's assumptions. The largest is 128 bytes for `scan_ungetc` and its resolved callees. These are upper bounds for the admitted direct-call closures with intact AAPCS call frames, matching compiler metadata, normal memory, and no asynchronous exception. They are not bounds for their callers or for arbitrary corrupted return addresses. The report's `known_path_bytes` omits unknown frames and is only a diagnostic sum; it is neither a measured peak nor a proven upper or lower bound.

The real reset/main, SysTick, GPIO, I2C, UART, HardFault, and default-exception roots remain unresolved. NMI has an eight-byte closed synchronous chain; exception entry itself is additional. ARMv6-M exception stacking requires 32 bytes plus possible four-byte alignment. Nested handlers require their own frames and hardware exception frames; priority, masking, preemption, and callback reachability must be established before any whole-image calculation. See `mspm0-exceptions.md` for the emulator's supported architectural behavior and primary references.

Useful next dynamic scenarios include parser→command→sscanf at maximum accepted input, configuration compaction while logging is active, and interrupts at those deepest execution points. Tests should monitor all MSP/PSP writes and writes below `0x20000820`, and include a deliberately too-small stack guard as a negative control. Dynamic absence of a collision still covers only those executions; universal safety needs resolved callback targets, exception nesting, assembly frames, and recursion invariants.

`tests/test_physical_stack_audit.py` has seven passing regression groups: direct/conditional edges, unknown callbacks, recursion propagation, closed-graph sums, the variadic-frame discrepancy with a changed-prologue negative control, growing-stack loops/dynamic SP, and literal/undecoded bytes. Source and test files are frozen for the parent's full-suite checkpoint.
